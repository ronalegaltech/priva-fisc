# Starknet contracts

| Package | What it is |
|---|---|
| `pf_batch_k10_verifier` | Generated by Garaga (`ultra_keccak_zk_honk`) from the verification key of `noir/batch_k10`. |
| `pf_agg_top_verifier` | Generated the same way from `noir/agg_top`, the final proof of an aggregate. |
| `pf_debtor_k10_verifier` | Generated the same way from `noir/debtor_k10`, 1 to 10 invoices issued to one buyer. It is the Montenegrin circuit: no verifier is generated for the Albanian one (`noir/debtor_al_k10`), so proofs over Albanian files are checked off chain only; the same holds for `noir/einvoice_al_k10`. |
| `pf_registry` | Calls the right verifier, accepts a proof only if its authority key hash is listed by the registry owner, refuses a presentation whose nullifiers were seen before, and records what was proved. A context takes batches and proofs about one buyer together (they publish the same nullifier per invoice) or aggregates, because a nullifier per invoice and a scope nullifier cannot be compared with each other. For an aggregate it also checks that the proof was built from the leaf, node and sorted-list circuits the registry was deployed with, and takes the number of invoices from the proof. It never stores invoice data. |

Do not edit the generated packages; regenerate them. They are tested through `pf_registry`.

```sh
. tools/toolchain.env
(cd starknet/pf_registry && snforge test)      # 24 tests against real proofs
sh tools/starknet/refresh_fixture.sh           # after any circuit change
sh tools/starknet/devnet_demo.sh               # the whole flow on a local network
sh tools/starknet/sepolia_demo.sh              # the same flow on Starknet Sepolia; needs a funded account
```

A verifier embeds its circuit's verification key. After any change under `noir/`, run
`refresh_fixture.sh`, otherwise the contracts reject proofs of the new circuits.

On a local network (starknet-devnet) the flow runs end to end for the three kinds of proof:
declare, deploy, list the authority key, submit (accepted: about 865M L2 gas for the batch of 10,
861M for 3 invoices to one buyer, 822M for an aggregate of 25), submit the same proof again
(refused with `invoice already presented`). Three invoices of the batch, proved once more as
invoices issued to their buyer, are refused the same way: a valid proof of another kind about
invoices the registry has already recorded. The
cost of an aggregate does not depend on how many invoices it covers. Starknet documents a limit of
1.11 * 10^9 L2 gas per transaction.

The same flow ran on the public test network (Starknet Sepolia) on 20 Nov 2026, with
`tools/starknet/sepolia_demo.sh`. The invoices were invented and signed by throw-away keys.

| aggregate of 25 | `0x05d18977a64e6db8094fa8c630eaf6bcc0d9a0cc67133b38896b55d96e068ee0` | 822,454,160 | 23.0 STRK |

The registry is at `0x007963f970475a3c410b260b6b3335f4449f87a0f8e5e4961cb1e93df296cf19` and holds
three attestations. Each proof was submitted a second time and refused with
`invoice already presented`, and so were the three invoices of the batch proved again as invoices
issued to their buyer. Nothing is deployed to mainnet.

Declaring is most of the cost: 53 STRK for the ECIP helper, 135, 133 and 135 STRK for the three
verifiers and 17 STRK for the registry (locally about 1.9 * 10^9 L2 gas, 4.8 * 10^9 each and
0.6 * 10^9). With the account, the deployment of the registry and the listing of keys the whole
run came to 545 STRK at a gas price of about 28 * 10^9 fri. With the batch alone it would be about
230 STRK. This is test-network money; what the same gas costs on mainnet has not been measured.

Two things to know about that run. sncast's own fee bound (the estimate plus a half) was refused by
Sepolia for a proof (`maximum allowed gas amount: 1210000000`), so the script estimates first and
sends with bounds it works out itself. Two attempts stopped there before the script was changed;
each had already listed the key of its throw-away signer, so the registry lists five keys and has
attestations under three of them.

The registry records the context a proof was made for; it cannot know which context a relying
party issued. The first attestation in a context decides which kind of proof that context takes,
so a relying party keeps a context to itself and the taxpayer until its attestation is recorded.
A scope (taxpayer key, unit, device, year) gets one aggregate per context, even if a later one
would cover more invoices. Nothing is ever withdrawn: what a later spot check finds is for the
relying party to keep. A relying party reads only the attestations in its own context. `submitted_by` is
the account that sent the transaction: a proof is not bound to its sender, so this is information
about the transaction, not about the taxpayer.
