# Starknet contracts

| Package | What it is |
|---|---|
| `pf_batch_k10_verifier` | Generated by Garaga (`ultra_keccak_zk_honk`) from the verification key of `noir/batch_k10`. |
| `pf_agg_top_verifier` | Generated the same way from `noir/agg_top`, the final proof of an aggregate. |
| `pf_debtor_k10_verifier` | Generated the same way from `noir/debtor_k10`, 1 to 10 invoices issued to one buyer. It is the Montenegrin circuit for requests of up to 2,048 bytes: no verifier is generated for the four circuits for longer requests (`noir/debtor_k7_m4096`, `debtor_k4_m8192`, `debtor_k2_m16384`, `debtor_k1_m32768`) or for the Albanian ones (`noir/debtor_al_*`), so proofs about longer invoices and proofs over Albanian files are checked off chain only (each verifier is a contract of its own, and declaring one cost about 135 STRK on Sepolia, see below); the same holds for `noir/einvoice_al_k10`. |
| `pf_registry` | Calls the right verifier, accepts a proof only if its authority key hash is listed by the registry owner, refuses a presentation whose nullifiers were seen before, and records what was proved. A context takes batches and proofs about one buyer together (they publish the same nullifier per invoice) or aggregates, because a nullifier per invoice and a scope nullifier cannot be compared with each other. For an aggregate it also checks that the proof was built from the circuits the registry was deployed with (one commitment to the key hashes of the leaf circuits, of which there is one per length of request, and the key hashes of the node and sorted-list circuits; `tools/efi/agg.py circuits` prints the three values), and takes the number of invoices from the proof. It never stores invoice data. |

Do not edit the generated packages; regenerate them. They are tested through `pf_registry`.

```sh
. tools/toolchain.env
(cd starknet/pf_registry && snforge test)      # 24 tests against real proofs
sh tools/starknet/refresh_fixture.sh           # after any circuit change
sh tools/starknet/devnet_demo.sh               # the whole flow on a local network
sh tools/starknet/sepolia_demo.sh              # the same flow on Starknet Sepolia; needs a funded account
```

A verifier embeds its circuit's verification key. After any change under `noir/`, run
`refresh_fixture.sh`, otherwise the contracts reject proofs of the new circuits.

On a local network (starknet-devnet) the flow runs end to end for the three kinds of proof:
declare, deploy, list the authority key, submit (accepted: about 864M L2 gas for the batch of 10,
860M for 3 invoices to one buyer, 822M for an aggregate of 25), submit the same proof again
(refused with `invoice already presented`). Three invoices of the batch, proved once more as
invoices issued to their buyer, are refused the same way: a valid proof of another kind about
invoices the registry has already recorded. The
cost of an aggregate does not depend on how many invoices it covers. Starknet documents a limit of
1.11 * 10^9 L2 gas per transaction.

`tools/starknet/sepolia_demo.sh`, from a separate clone of this repository at commit `4096432`,
after the full test run had passed in that clone. The invoices were invented and signed by
throw-away keys.

A verifier holds the verification key of its circuit, and the registry holds the values an
aggregate must name for the circuits it was built from. After a change to one of these circuits
the packages here are generated again and the contracts on Sepolia stay as they were, until the
script is run again: the hashes above tell whether the two still agree.

Declaring is most of the cost: 137, 135 and 137 STRK for the three verifiers and 18 STRK for the
registry (4.81, 4.74 and 4.81 * 10^9 L2 gas, and 0.62 * 10^9). The ECIP helper was already
declared (53 STRK on 20 Nov 2026) and the account already existed. With the deployment of the
registry and the listing of three keys the run came to 498 STRK at a gas price of 28.4 * 10^9
fri. This is test-network money; what the same gas costs on mainnet has not been measured.

An earlier run, on 20 Nov 2026, put the circuits of that day on Sepolia: its registry is at
`0x007963f970475a3c410b260b6b3335f4449f87a0f8e5e4961cb1e93df296cf19`, and with the helper and the
account it came to 545 STRK. The circuits changed afterwards (the request reader on 22 Nov 2026,
the leaves of an aggregate on 23 Nov 2026) and with them their verification keys, so the
contracts of that run accept proofs of the circuits of that day only.

Two things to know about the earlier run. sncast's own fee bound (the estimate plus a half) was
refused by Sepolia for a proof (`maximum allowed gas amount: 1210000000`), so the script estimates
first and sends with bounds it works out itself. Two attempts stopped there before the script was
changed; each had already listed the key of its throw-away signer, so the earlier registry lists
five keys and has attestations under three of them.

The registry records the context a proof was made for; it cannot know which context a relying
party issued. The first attestation in a context decides which kind of proof that context takes,
so a relying party keeps a context to itself and the taxpayer until its attestation is recorded.
A scope (taxpayer key, unit, device, year) gets one aggregate per context, even if a later one
would cover more invoices. Nothing is ever withdrawn: what a later spot check finds is for the
relying party to keep. A relying party reads only the attestations in its own context. `submitted_by` is
the account that sent the transaction: a proof is not bound to its sender, so this is information
about the transaction, not about the taxpayer.
